# Development

## Run and verify

Implementation stages run focused changed-path/security tests, build/typecheck and lint for touched workspaces. After an authorized implementation commit, push the current branch to its configured remote unless the user explicitly requests otherwise; never force-push or overwrite unrelated remote work. Full historical E2E, broad browser/viewport matrices and load benchmarks belong to Final Validation unless a concrete regression requires them. Critical authorization failures must be fixed before delivery.

Use pnpm 11.19.0; project scripts select Node 24.21.0. Copy `apps/web/.env.example` to `apps/web/.env.local` and `apps/api/.env.example` to `apps/api/.env` on a new checkout. Supply real values locally only.

```sh
pnpm install --frozen-lockfile
pnpm dev                 # Web :4000, API :9000; Ctrl+C stops both
pnpm dev:web             # Web only :4000
pnpm dev:api             # API only :9000
pnpm build
pnpm lint
pnpm typecheck
pnpm test                # API domain/security + migration replay and web node tests
pnpm test:e2e            # full real dev suite; reserved for Final Validation or a concrete regression
pnpm openapi             # after API build; exports spec and generated types
pnpm smoke --api=<url> --web=<url> [--production]   # unauthenticated post-deploy checks
```

Local Web: `http://localhost:4000` (fixed by both `dev` and `start` scripts). Local API: `http://127.0.0.1:9000`; `WEB_ORIGIN=http://localhost:4000`. Keep local env files aligned with their examples, including `NEXT_PUBLIC_API_BASE_URL`. These ports belong to this Rental project; do not stop another project's listener when a conflict occurs.

API prefix: `/api/v1`. Swagger: `/api/docs`; JSON: `/api/openapi.json` (disabled in production). Errors contain `statusCode`, `code`, `message`, `requestId`, without database/provider details. Standard lists accept `page` (default 1) and `limit` (default 20, maximum 100), with stable ID tie-breaking. Dates use explicit UTC offsets and API output is UTC ISO; the UI formats operational times in `Asia/Ho_Chi_Minh`.

Ask before starting a server unless the user has already authorized it for the task. Record owned sessions/PIDs/ports; stop temporary servers, watchers and containers on completion/failure and verify they exited. Retain dev servers only when the user requests it. Never stop unrelated/user-owned processes or use broad kill commands.

## Architecture and security

- Web uses per-request Supabase SSR clients, cookie refresh in `proxy.ts` and protected server layouts. It forwards bearer tokens to NestJS; browser code receives only the publishable key. A business switch reloads the document so prior tenant form/list/map state cannot survive.
- NestJS verifies Supabase Auth, then active profile, business and membership. Optional `X-Business-Id` selects a verified active membership; otherwise the oldest active membership is selected. Never authorize with `user_metadata`, a browser-supplied business ID, hidden menu or frontend state.
- The application has two active surfaces: Superadmin (internal platform role `PLATFORM_OPERATOR`) and business `OWNER`. Owner receives the existing tenant operational permissions; legacy ADMIN/OPERATIONS and Customer receive none. Member creation accepts only `userId` and always grants OWNER; update accepts only required ACTIVE/DISABLED `status`. Role selection/hierarchy and permission matrices/counts are removed from UI. The last effective active Owner cannot be disabled. Backend permission guards remain independent of UI and metadata.
- Every tenant resource query includes the verified business ID. Platform read APIs use independent active platform membership/profile/permission checks and return approved global metadata/aggregates; a tenant role or selected-business header never grants global access. Mutations acquire the business row lock, recheck current profile/business/membership/permission and write the resource and audit event in one transaction. Membership revocation and domain writes share that lock. Unique/exclusion constraints provide a second concurrency defense.
- Audit metadata contains request IDs and changed field names, not bodies, coordinates, tracker identifiers, credentials, contacts, notes or amounts. Wrapped database errors map to stable public conflict codes.
- Exposed tables enable RLS. Tenant registry/customer/rental Data API reads require active membership/profile/business; direct writes by `anon`/`authenticated` are revoked. `gps_positions` denies all Data API reads and writes, with RLS enabled and no read policy. The API's trusted database connection still must enforce tenant authorization itself. No `SECURITY DEFINER` authorization helper is used.
- Generated OpenAPI and TypeScript contracts live in `packages/contracts`; regenerate after API changes. Database schema, credentials and provider secrets remain server-only.

Domain boundaries are `apps/api/src/fleet/vehicles`, `apps/api/src/rentals`, `apps/api/src/commercial`, `apps/api/src/alerts`, `apps/api/src/telematics/{gps,trips}` and the independently authorized `apps/api/src/platform`. Web live features follow `features/fleet/vehicles`, `features/rentals`, `features/commercial`, `features/alerts` and `features/telematics/{gps,trips}`; synthetic business examples live in `features/previews/business`; platform live components/data access are under `features/platform/live`, alongside the separate development preview. Shared UI/data-display/overlay components contain presentation behavior rather than tenant business rules. Routes and API payloads remain stable during structural moves.

The Owner-only migration refuses while any legacy non-OWNER membership remains, including disabled rows. Resolve those identities explicitly before applying it; the migration never promotes staff into Owner or deletes historical data. It restricts the DB check to OWNER and tenant audit RLS to active Owner/profile/business. Current Auth account-type labels are descriptive only and are not authorization inputs.

## Platform console

`/superadmin`, `/superadmin/businesses`, `/superadmin/businesses/:id`, `/superadmin/audit`, `/superadmin/users` and `/superadmin/users/:id` are live platform views. Superadmin can provision businesses/Owners, issue private recovery links and suspend/reactivate businesses; it has no tenant operational read/write grant. Every role uses the same `/login` form and copy; no workspace or role picker exists. After Supabase sign-in persists cookies, the browser visits `/auth/continue`, which verifies the identity and checks NestJS grants on the server without a selected-business header. A safe `next` hint selects which independent grant to check first; 200 preserves that authorized deep link, 403 permits checking the other surface. A stale role-specific link falls back to the granted workspace. Without a hint, tenant `/me` is checked before `/platform/me`. Both 403 results lead to access denied; network/unexpected responses fail closed back to the same form. Protected layouts independently reauthorize each destination. Local return paths allow only `/app` or `/superadmin` descendants, normalize traversal and reject external/control/out-of-scope destinations. No email or Auth metadata grants access.

Supabase supplies identity only. `AuthGuard` verifies the current user; `PlatformGuard` checks an ACTIVE `user_profiles` row plus an independent ACTIVE `platform_memberships` row with role **PLATFORM_OPERATOR**. Tenant OWNER, retired roles, `user_metadata`, the business cookie and `X-Business-Id` are never platform grants. A platform-only operator receives no tenant operational permission; a user requiring both surfaces needs both independently reviewed memberships. Browser code sees no server key.

| API (relative to `/api/v1`)    | Permission / behavior                                                                                                                                                                                                 |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /platform/me`             | Independent principal, read permissions and `readOnly:false`; no tenant context or email projection                                                                                                                    |
| `GET /platform/overview`       | `platform.overview.read`; current totals across all businesses, including disabled ones                                                                                                                               |
| `GET /platform/businesses`     | `platform.business.read`; page/limit ≤100, literal name search ≤120 chars, ACTIVE/DISABLED filter, allowlisted name/createdAt ordering with stable ID ties                                                            |

Business projections contain name/status/timezone/currency/timestamps plus branches, membership rows, vehicles/rentals and current-assignment GPS freshness counts. Active membership requires both membership and profile ACTIVE; totals include disabled businesses, and membership counts are not globally unique people. GPS is always TEST and follows the existing 120/600-second thresholds. The API does not return user contacts, customer records, raw device identities, coordinates, history, notes or settings. Aggregations happen in SQL for the selected page/businesses, without browser tenant loops or per-tenant requests.

Every successful platform read locks and rechecks the operator/profile in the transaction that reads data and inserts `platform_audit_logs`; failed recheck or audit failure prevents delivery. Metadata records only a server request ID; targeted business/user IDs are separate fields with explicit entity types. Platform audit is independent of tenant `audit_logs`. The two platform tables have RLS enabled, no browser policies and all privileges revoked from PUBLIC/anon/authenticated, including for an authenticated platform operator. The API's trusted DB connection must still perform all platform authorization. There are no direct browser database grants. Platform administration is limited to business/Owner provisioning, access-link issuance and business status, with independent write permissions and platform audit.

The previous dedicated demo bootstrap is retired for configured named accounts; `platform:seed` refuses retired fixtures. Provision actual Superadmin access through an explicit trusted administrator process. The internal name `PLATFORM_OPERATOR` is kept for the existing platform DB/API boundary; the UI displays **Superadmin**. Self-service platform signup remains unavailable; provisioning never grants PLATFORM_OPERATOR. The approved platform write endpoints are listed below.

Audit returns only ID, actor UUID reference, allowlisted action/entity type, target UUID, timestamp and UUID-shaped server request ID; raw metadata is never returned. Unreviewed actions/entity types become `other`, unknown targets and malformed request IDs are omitted/null. A business filter matches only direct business-targeted platform events, never tenant audit. Viewing audit itself is audited after the returned snapshot. Filters use a fixed returned time window when paginating.

Users are registered application profiles, not an enumeration of Supabase Auth identities. Each list row counts one person regardless of tenant membership count. Support projection includes ID/display name/profile status, platform grant status, timestamps, Owner summary and membership counts. Detail memberships expose business ID/name/status and membership role/status only. `activeMembershipCount` requires profile, membership and business ACTIVE; this is deliberately stricter than Overview's active membership count, which includes disabled businesses. Contacts, Auth metadata, credentials, customers and raw telemetry are excluded. These user-support screens do not offer impersonation, identity disabling or role management. Owner recovery links are issued only from the independently authorized business workflow described below.

`/superadmin/features`, `/integrations` and `/settings` are read-only views over `GET /platform/system` (`platform.system.read`, platform-audited as `platform.system.read`). The response contains only the environment name, DB reachability, latest applied migration, configured/not-configured booleans, the Supabase host, fixed ingress/evidence/report limits and a static feature catalogue marking GPS as TEST and the Customer portal, online payments, notifications and billing as not implemented. It never returns keys, tokens, database URLs or emails, and there are no write controls. Entitlements, billing and general identity-management writes are not implemented; business suspension/reactivation is available through the reviewed platform business endpoints. Development design previews remain a separate labelled surface and are excluded from production.

## Business and Owner onboarding

Superadmin opens Doanh nghiệp → Tạo doanh nghiệp, enters the initial branch and Owner email/display name, then privately shares the one-time access link. Owner opens the app confirmation link, sets their own password and continues into the verified business workspace. Existing Auth users may own multiple businesses; provisioning adds OWNER membership without changing an existing password, profile name/status or platform grants. A disabled profile cannot be silently reactivated. Owner and Customer have no platform management permission.

`POST /platform/businesses` requires `platform.business.create`; `POST /platform/businesses/:id/owner-links` requires `platform.owner.access` for an active Owner/profile in that active business; `PATCH /platform/businesses/:id/status` requires `platform.business.manage`. Writes recheck the independent active platform principal and use platform audit only. Business status shares the tenant row lock with operations, so DISABLED denies subsequent tenant reads/writes; reactivation restores only existing active memberships. The business detail exposes bounded Owner membership IDs/display names/status for support, never tenant customers/contracts or Auth emails.

Auth Admin uses the API-only `SUPABASE_SECRET_KEY`; recovery generation does not send SMTP email. Private links are returned with no-store and exist only in component state until dismissed. Never paste them into tickets, analytics, Git, screenshots or audit. The recipient URL necessarily carries the one-time hashed credential until `/auth/confirm` consumes it; the handler rejects other OTP types, ignores redirect parameters and redirects to a clean `/set-password` URL with a no-referrer policy. The business UUID is a selection hint only; NestJS independently verifies every grant. No new throttling dependency is installed; reverse-proxy rate limits and monitoring are required before production.

Dashboard checklist for **each environment**, never implied by local `config.toml`: disable public/email signup; review password minimum/strength policy (the app minimum matches the checked-in configuration); allowlist `${WEB_ORIGIN}/auth/confirm`; review recovery OTP expiry for private delivery (up to 24 hours for this workflow, shorter when practical); enable leaked-password protection when supported by the plan. Local config disables signup. Hosted settings must be verified/applied separately by the project administrator; no production setting is changed by an implementation stage. Keep keys server-only and TLS verification enabled. Copied link delivery and password setting remain human actions for provisioning; automatic provisioning emails, billing and online payments are deferred. Self-service **forgot password** is available at `/forgot-password`: it calls Supabase `resetPasswordForEmail`, always shows the same notice (no account enumeration, provider errors ignored) and the emailed link opens the existing `/auth/confirm` → `/set-password` flow with a one-time token hash. For it to work, each Supabase project needs working SMTP, the `recovery` email template from `supabase/templates/recovery.html` (use `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=recovery`), the Site URL/redirect allowlist for the Web origin and a suitable email rate limit; `supabase config push` or the Dashboard applies them and no stage changes hosted settings automatically. Disabled profiles/memberships can receive the email but are still denied by `/auth/continue`.

## Fleet registry and assignment

`/app/vehicles`, `/app/vehicles/devices` and `/app/vehicles/:id` are live tenant-authorized pages. Vehicle lifecycle is `ACTIVE`/`INACTIVE`; rental availability and GPS freshness are independent derived concepts. A registry entry or assignment does not mean a tracker is online.

OWNER has `vehicle.read/manage` and `gps.read/manage`. Assign/end requires `vehicle.manage`. New branch associations require an active branch belonging to the verified tenant.

License plates are uppercased with whitespace/dot/hyphen removed, then validated as 4–16 ASCII letters/digits. The canonical plate is unique within the business, including inactive vehicles. GPS `provider` is lowercase and `deviceUid` trimmed but case-sensitive; `(provider, deviceUid)` is globally unique. Provider, UID and business ownership are immutable; PATCH changes only device label/status.

Each vehicle/device has at most one current primary assignment, enforced by partial unique indexes. Composite tenant foreign keys prevent mixed ownership. End the current assignment before disabling a resource or replacing its device. Assignment/end timestamps use `clock_timestamp()` after locking, with end bounded by assignment start. Ended history cannot be rewritten; there are no hard-delete or cross-business transfer APIs. Vehicles with RESERVED/ACTIVE rentals cannot be disabled.

All endpoints below are relative to `/api/v1` and require Supabase authentication plus verified tenant permission:

## Vehicle compliance and service history

Vehicles carry optional `registrationExpiresOn`, `insuranceExpiresOn`, `nextMaintenanceOn` (calendar dates, years 2000–2099, `null` clears) and `nextMaintenanceOdometer`. `GET/POST /vehicles/:id/service-records` (`vehicle.read/manage`) lists and appends MAINTENANCE/REGISTRATION/INSURANCE history (`performedOn` cannot be a future Vietnam date; optional odometer, exact whole-VND `costVnd`, notes ≤2,000). A record may carry `nextDueOn` (and `nextDueOdometer` for maintenance) to update the matching vehicle date in the same locked transaction as the record and redacted `vehicle_service.create` audit. `vehicle_service_records` is append-only (trigger), tenant-composite-FK scoped, Owner-read RLS, browser writes revoked. Recorded cost is informational: it never creates a Commercial movement.

Alerts add `VEHICLE_REGISTRATION_DUE`, `VEHICLE_INSURANCE_DUE` and `VEHICLE_MAINTENANCE_DUE` for ACTIVE vehicles: a date before today (Asia/Ho_Chi_Minh) is CRITICAL, today through the next 30 days is WARNING. They are hidden when a rental filter is selected and counted in `stats.vehicleCompliance`. Odometer-based maintenance has no alert because no live odometer exists.

## Customer and Rental Core

Live routes: `/app/customers`, `/app/customers/:id`, `/app/rentals`, `/app/rentals/new` and `/app/rentals/:id`. Dashboard schedule/active queue and Vehicle Detail current/next rental use real Rental API data. OWNER has `customer.read/manage` and `rental.read/manage`.

Customer names are trimmed, 1–120 characters; phone or email is required. Phone accepts 5–32 characters (digits, spaces/hyphens, optional leading `+`); email is trimmed/lowercase, maximum 254 characters. Contacts may be shared and are nonunique. Notes are at most 2,000 characters. Disable rather than hard-delete; a customer with RESERVED/ACTIVE rentals cannot be disabled. Historical rentals retain customer references.

Lifecycle: `DRAFT → RESERVED → ACTIVE → COMPLETED`; DRAFT/RESERVED may become CANCELLED. Handover records database time and `odometerStart`; return records database time and `odometerEnd`, at least the start reading. Odometers are integers 0–2,147,483,647. Invalid/repeated transitions conflict without duplicate milestones/audit events. `OVERDUE` is derived from ACTIVE + elapsed `endAt`, never stored as a workflow status. Vehicle display can be AVAILABLE/RESERVED/RENTED/OVERDUE without changing lifecycle or GPS status.

Drafts do not hold vehicles. Reserve requires an active vehicle/customer, unexpired interval and availability; handover is allowed only during the planned interval and while no other rental holds the vehicle. RESERVED/ACTIVE rentals block half-open UTC intervals `[startAt,endAt)`; adjacent reservations may share an endpoint. PostgreSQL GiST exclusion uses `btree_gist` in `extensions` to prevent overlap, plus a partial unique index permits only one ACTIVE rental per vehicle. An overdue unreturned vehicle remains unavailable after its old planned end. Existing future reservations stay visible but cannot hand over until the actual rental returns. Reserve/Extend recheck conflicts under the business lock.

Draft PATCH may change customer/vehicle/interval/amounts/deposit/notes. RESERVED/ACTIVE PATCH changes amounts/deposit/notes only; interval extension uses the action endpoint. Terminal rentals are read-only. Amounts are JSON numbers 0–999,999,999.99 with at most two decimal places, stored as exact `numeric(14,2)`. ## Customer portal

`/portal`, `/portal/rentals/:id` and `/portal/rentals/:id/contract/:version` are a read-only surface for a rental customer. A portal identity is a Supabase Auth user with an ACTIVE `user_profiles` row linked by `customer_portal_accounts` (unique per user and per customer, composite tenant FK, RLS enabled, no browser grants) to one ACTIVE customer of an ACTIVE business. It is never a business or platform membership and receives no tenant or platform permission; Owner/Superadmin routes keep denying it. `CustomerGuard` and every `/portal` query re-verify that link, so `X-Business-Id`, `user_metadata`, email and the business cookie never select a customer.

`GET /portal/me`, `/portal/rentals` (paginated, DRAFT hidden), `/portal/rentals/:id` and `/portal/rentals/:id/contract/:version` return only the verified customer's own rentals and issued contract snapshots (404 otherwise). Internal notes, staff user IDs, pricing override reasons, GPS and inspection/evidence data are never returned; contracts keep their immutable snapshot. Amounts are the contracted values, not proof of payment: there is no online payment, booking, notification or document upload.

Owner grants access from Customer detail: `GET/POST /customers/:id/portal-access` (`customer.read`/`customer.manage`). POST requires an ACTIVE customer with a valid email, creates a new confirmed Auth user and returns a private one-time recovery link (no-store, never emailed, never audited). It refuses an email that already has any account (`PORTAL_EMAIL_IN_USE`) so an Owner cannot take over another person's identity, and reissue is allowed only for the customer's own portal identity when it has no business/platform membership. The write locks the business, rechecks the Owner and records a redacted `customer.portal_access.issue` audit event. ## Rental pricing and quotation

## Evidence retention and holds

Retention is a business operating policy, not a statutory period. Each business defaults to **30 days after a valid COMPLETED rental's returnedAt**, configurable to **30 or 90 days**. ACTIVE/RESERVED/unfinished/CANCELLED rentals and legacy records without a valid completion timestamp never silently qualify. Disabled tenants are excluded from cleanup. Stage 14 snapshots and Stage 15 attachment metadata remain immutable; separate `evidence_lifecycles` rows track ACTIVE → PURGE_ELIGIBLE → PURGING → PURGED or RETRY_REQUIRED. Existing attachments are backfilled and new ones receive lifecycle state transactionally through a security-invoker insert trigger. PURGED rows and retention event history cannot be changed or deleted.

Owner APIs: GET/PATCH `/evidence/retention/settings` (`settings.read/update`, `{retentionDays:30|90}`); GET `/evidence/storage-usage` (`settings.read`); GET/PATCH `/rentals/:id/evidence/hold` (`rental.read/manage`, `{active,unresolvedDispute,reason}`); PATCH `/rentals/:id/evidence/:evidenceId/important` (`rental.manage`, `{important,reason}`). Important protects one file; a rental-level Legal hold protects the entire case, including both inspection milestones and future evidence. Holds override deadlines indefinitely and release is always explicit, with a nonblank reason (1–2,000 trimmed characters). Unresolved disputes require an explicit resolution/release, never a rental-status inference. Owner actor/time/reason history is append-only; general tenant audit contains only changed field names/request IDs. Background events identify a system actor, using null actorId in dedicated retention history and the reserved zero UUID plus SYSTEM metadata in general audit; this is not an Auth identity or permission grant.

All reads/writes recheck the active Owner/profile/business under the same tenant lock used by lifecycle operations. Protection changes reject PURGING or uncertain RETRY_REQUIRED media; Important also rejects PURGED. Policy changes reject a business with in-flight/uncertain deletes. This prevents a successful hold/extension response from promising protection after a deletion may already have happened. A hold can protect remaining media in a partly purged case, but never restore removed files. Browser writes to all four retention tables are revoked and RLS permits only current active Owners to read their tenant. Download uses GET `/rentals/:id/evidence/:evidenceId/download`, with a fresh private attachment URL and a server-generated filename. Both read/download refuse expired, PURGING, RETRY_REQUIRED and PURGED media; new URL TTL is at most 60 seconds and bounded by the remaining retention window. Previously issued/downloaded content is not retrospectively revoked. Important/Legal hold can preserve an expired but unclaimed object and restore authorized reads; a purged object is permanently unavailable.

The trusted `evidence:retention` command scans one bounded candidate page (default20, maximum100), and **dry-run performs no mutations/deletions**. Apply requires both `--apply` and `EVIDENCE_RETENTION_DELETE_ENABLED=true`, with APP_ENV=development and exact project eeryymswcufnebibigqf; the flag remains false by default and has no Owner UI switch. Each object is claimed with an exclusive 90-second lease, then deletion rechecks current policy, hold, attachment, tenant state and lease under the business lock. The lock is held through Storage API deletion and tombstone/audit commit. Missing objects are idempotently removed; partial batch failures do not fail unrelated files. Failures retain an unavailable RETRY_REQUIRED state with exponential backoff (one minute up to one day). Expired leases recover through a new claim; stale workers cannot finalize newer claims. If Storage succeeded but the database commit failed, retry reconciles the uncertain state without reopening a broken preview. Final-file quota is released only after acknowledged removal; any pending object retains its reservation until the existing Stage 15 capability-safe janitor removes it. No direct Storage SQL deletion, production cleanup scheduler or deployment is introduced.

## GPS ingestion and current location

The only verified source is a **Traccar TEST feed** through its real decoder, authenticated ingestion, database and API. Adapter/storage/UI fix `sourceMode: TEST`; input cannot promote it to REAL. Feed coordinates are synthetic. No physical tracker, durable external provider or production deployment is verified.

`POST /api/v1/integrations/traccar/positions` accepts the Traccar JSON forwarding envelope (`device`, `position`). Set server-only `GPS_TRACCAR_TOKEN` to at least 32 random characters in the ignored API env; an empty/short value disables ingestion with `GPS_NOT_CONFIGURED`. Traccar sends `X-Traccar-Token`; constant-time hash comparison rejects missing/incorrect credentials with `INVALID_GPS_TOKEN`. This trusted webhook credential is separate from Supabase user auth and never reaches browser env or logs.

Webhook-only controls authenticate before JSON parsing, accept uncompressed JSON up to **16 KiB**, and reject invalid JSON/media/encoding with secret-safe 400/413/415 envelopes. Other API routes retain Nest's normal body-parser settings. Limits are **600 requests / 60 seconds per process**, **120 valid packets / device / window**, **16 concurrent ingress requests**, and at most **1,024 hashed identity buckets** cleared each window. Rejected authentication attempts consume the global quota. Quota errors return 429 `GPS_RATE_LIMITED` with `Retry-After` (1–60 seconds); semantic duplicates still consume capacity and remain idempotent in storage. Provider retries must honor the delay. These fixed-window, process-local controls are not a distributed quota or durable queue.

A `gps_ingress_window` structured event reports only fixed aggregate outcome counters when the next request advances a 60-second window. It contains no raw UID, IP, coordinates, body or token; `LOG_REQUESTS=false` disables these logs. Before external provider exposure, configure gateway per-source connection limits and a shorter body/read timeout: Node's current request deadline is five minutes, so slow authenticated bodies can occupy the bounded ingress slots until then. No external gateway/provider deployment is enabled automatically.

The adapter maps only canonical fields, not raw provider packets:

| Field                       | Validation/source                                                                                           |
| --------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `provider`, `deviceUid`     | Fixed `traccar`; case-sensitive `device.uniqueId`                                                           |
| `recordedAt`, `receivedAt`  | Strict timezone-qualified `position.fixTime`; database clock on first receipt                               |
| `latitude`, `longitude`     | Finite numeric degrees in −90…90 and −180…180                                                               |
| `speedKph`, `heading`       | Knots ×1.852, finite 0…600 km/h; course finite 0 ≤ degrees <360                                             |
| `ignition`                  | Boolean `position.attributes.ignition`, null when absent                                                    |
| `sourceEventId`, `eventKey` | Optional positive safe-integer provider ID; SHA-256 of UID/fix/coordinates/normalized speed/course/ignition |
| `sourceMode`                | Server-fixed/database-constrained `TEST`                                                                    |

Only `position.valid === true` is accepted. Invalid values return `INVALID_TELEMETRY`; fixes more than five minutes ahead of database time or more than 30 days old return `GPS_TIME_OUTSIDE_WINDOW`. Global immutable registry identity resolves the business; incoming business/vehicle IDs are ignored. Under the business lock, ingestion checks active business/device and exactly one historical assignment containing `recordedAt` in `[assignedAt,unassignedAt)`. This includes ended assignments for delayed events; unresolved/ambiguous assignments are rejected. Composite `(businessId,assignmentId,deviceId,vehicleId)` ownership is enforced by a foreign key.

Unique `(deviceId,eventKey)` makes semantic retransmissions idempotent. Traccar memory-store IDs restart and are diagnostic only. Duplicates return the original position ID and `duplicate:true`, without changing first receipt time. Current location is the latest point of the current assignment ordered by `recordedAt DESC, receivedAt ASC, id ASC`, backed by `gps_positions_assignment_latest`; delayed points cannot move it backwards and equal-time ties retain the first accepted point. Ending/replacing an assignment immediately hides its old points from current location while preserving history. Device/vehicle time, retention and assignment identity indexes support the other access paths.

`GET /vehicles/:id/location` returns a scoped current projection or 404; `GET /fleet/locations` returns scoped paginated projections, optional `search/state`, tenant statistics, `asOf` and `pollAfterSeconds:20`. Both require `gps.read`. An active rental ID is exposed only with `rental.read`. Registry permissions and assignment do not establish a GPS signal:

| State        | Recorded fix age against server time                    |
| ------------ | ------------------------------------------------------- |
| `UNASSIGNED` | No current assignment                                   |
| `NO_DATA`    | Current assignment has no accepted fix                  |
| `FRESH`      | ≤120 seconds                                            |
| `STALE`      | >120 and ≤600 seconds                                   |
| `OFFLINE`    | >600 seconds; last-known coordinates may remain visible |

`GET /fleet/telemetry/diagnostics` requires `gps.read` and returns only the selected tenant's freshness counts and unique stored fixes/devices received in the last 15 minutes, last received/recorded times, `sourceMode:TEST`, ingestion-enabled state and fixed process limits. Duplicate requests do not increase stored-fix counts or change first receipt time. The response exposes no device/vehicle IDs, coordinates, credentials or cross-tenant failure counters; failure categories remain in aggregate internal logs.

`/app/fleet-map`, dashboard GPS and Vehicle Detail use these authorized projections with explicit **TEST FEED** labels. The live map plots/lists its current page of 20 vehicles, with vehicle/current-rental navigation. It polls 20 seconds after completion, pauses hidden tabs and aborts obsolete work on unmount/filter/tenant changes. Failed refresh retains the last response with a warning, last successful load time and an explicit retry button; 401/403 navigate to Login/access denied. STALE/OFFLINE descriptions identify coordinates as last recorded rather than confirmed current position. Vehicle Detail refreshes on page reload; history is not polled or downloaded by the current-location map.

## Derived Trip history and route replay

Trips are calculated on demand from existing `gps_positions`; there is no duplicate history table, persisted summary or new migration. OWNER receives `trip.read`; the same active-profile/business/membership guards and tenant predicates protect every Trip/filter/detail/route query. An opaque Trip ID is not an authorization credential. GPS ingestion and current-location selection remain separate and unchanged.

| Endpoint               | Query / response boundary                                                                                                  |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `GET /trips`           | Optional `vehicleId`, `rentalId`, `from`, `to`, `sort=asc/desc` (default desc), standard page/limit; default last 24 hours |
| `GET /trips/:id`       | One rederived summary in its original exact query window                                                                   |
| `GET /trips/:id/route` | Recorded points with page/limit; default and maximum 500 points per page, `total` and `hasMore`                            |

Ranges use `[from,to)`, require timezone-qualified timestamps, increase strictly and span at most **7 days**, with end no later than five minutes ahead. At most **10,000 candidate fixes** may be considered before trip-list pagination; denser ranges fail with 422 `TRIP_POINT_LIMIT` and must be narrowed. Invalid ranges/IDs return 400 `INVALID_TRIP_RANGE` / `INVALID_TRIP_ID`; unavailable or cross-tenant filter/detail resources return 404 `TRIP_NOT_FOUND`. Empty data is a valid empty list. Route paging bounds transfers rather than silently truncating server derivation.

Derivation sorts by recorded time, with first `receivedAt`/ID canonicalizing duplicate assignment/timestamp fixes. It uses each point's historical assignment resolved at ingestion, never today's device assignment. SQL selection and domain derivation both revalidate `recordedAt` within `[assignedAt,unassignedAt)`; a clock-skew-tolerated fix dated after its assignment later ended is excluded rather than attributed to another assignment. Assignment changes always split; gaps over **10 minutes** split without connecting a line. `ignition=false` with speed below **3 km/h** closes a segment. Movement requires a fix at least 3 km/h or a usable consecutive edge of at least **30 metres**; stationary-only groups are omitted. Consecutive Haversine distances are estimates, not odometer readings. Edges implying more than **250 km/h** are excluded from distance and carry `breakBefore:true` so replay never draws across the jump.

Each summary includes vehicle/assignment/device identity, optional inferred rental ID, UTC start/end and duration, estimated distance, point count, recorded/received freshness, `sourceMode:TEST`, `derivation:DERIVED`, `distanceKind:ESTIMATED`, route availability and partial reasons. A single moving fix stays a partial Trip with `INSUFFICIENT_POINTS` and no usable route. Unobserved starts/ends, gaps, assignment boundaries, conflicting ignition/movement, implausible position jumps and a query before the 30-day retention boundary are explicit limitations (`START_NOT_OBSERVED`, `END_NOT_OBSERVED`, `GAP_BEFORE/AFTER`, `ASSIGNMENT_BOUNDARY`, `IGNITION_CONFLICT`, `POSITION_JUMP`, `RETENTION_WINDOW`). `RANGE_START` additionally marks a segment whose assignment began before the query window without an observed preceding stop; the API does not claim that its first returned fix is the actual departure. Freshness uses the same 120/600-second recorded-time thresholds as current location and does not make historical replay live tracking.

Rental associations use tenant/vehicle-matching scheduled windows of RESERVED/ACTIVE/COMPLETED rentals. `CONTAINED` means the full derived segment fits the scheduled interval; `OVERLAP` means only a time intersection. Both carry `basis:SCHEDULED_WINDOW` and do not prove actual customer use. A scalar `rentalId` is set only for exactly one containing interval; the association list preserves overlaps. Filtering by Rental uses these associations without inventing a route across a boundary.

IDs encode the vehicle, start-fix ID and exact normalized query window, then detail/route rederive with authorization. Late fixes can change grouping or IDs; retention can remove a Trip or make it partial. Refresh the list when a saved detail returns unavailable. The not-found/error recovery link restores the encoded Vehicle/time filters after validation; these are untrusted navigation hints, and every resulting API request is authorized again. Malformed encoded IDs are shown as unavailable rather than a generic server error. Partial reasons describe observable limits; missing packets cannot be reconstructed.

`/app/trips` uses this live API with Vehicle/Rental/date filters and detail replay; Vehicle/Rental detail link to the corresponding filtered history. Leaflet replay draws only received bounded route points, honors line breaks and provides start/end markers and simple scrub/step controls. It does not poll history or fabricate missing points. Synthetic Trip examples stay under development-only previews.

## Commercial operations

`/app/commercial` is live for active Owner memberships. API routes are `GET/POST /commercial/movements`, `GET /commercial/movements/:id`, `POST /commercial/movements/:id/reverse`, `GET /commercial/summary` and `GET /rentals/:id/commercial`, relative to `/api/v1`. Independent platform membership and deferred Customer grant no financial access. Writes lock the business, recheck authorization and insert a redacted audit event atomically. RLS permits active Owner reads only; browser writes are revoked.

Movements use positive whole-VND strings up to 999999999999999 per entry, exact SQL numeric storage and BigInt calculations/display. Fractional commercial input is rejected. Existing Rental Core decimal amounts are compared after exact half-up rounding to whole VND; contracted rent and required deposits never count as receipts. Payments, miscellaneous income, deposits received/refunded/retained and categorized manual expenses are recorded separately. Rental-linked entries derive the vehicle; composite foreign keys enforce tenant/rental/vehicle consistency. Existing financial history prevents changing a rental's vehicle, including in draft, or the business currency. Non-VND businesses receive a stable unsupported-currency response. Completed/cancelled rental history is retained.

Corrections insert one exact mirrored reversal at current database time, with a required reason in its notes. Originals stay visible; reversal chains and duplicate reversals are denied. There are no financial PATCH/DELETE APIs. Deposit movements check every chronological cumulative balance under the tenant lock, rejecting over-refund/retention, invalid backdating and reversals that would create a negative balance. Date input requires an offset and cannot be in the future. Records are immutable through API/browser permissions; trusted database maintenance remains an administrative responsibility.

The summary basis is `RECORDED_MOVEMENTS`. Recorded revenue is rental receipts + miscellaneous income + retained deposits. Operating cash received excludes deposits and retention; net operating cash flow subtracts expenses. Estimated profit subtracts recorded expenses from recorded revenue and excludes unrecorded costs; it is not an accounting statement. Deposit held is cumulative receipts less refunds/retention through `until`, independent of `from`. Revenue/expenses use `[from,until)`; omitted dates mean all history through database time. Reversals affect their own occurrence date, retaining earlier-period history. Vehicle/rental filters apply to both summary and list; category/status/search apply only to the list and are labelled accordingly. Rental Detail shows actual receipts, outstanding/overpaid rent and deposit balance; Vehicle Detail links to its filtered Commercial view.

UI uses shared controls, paginated server-backed record pickers, immutable movement detail and correction flows, with exact currency formatting. No fixture KPI, payment processor, VETC sync, invoicing, VAT bookkeeping, double-entry ledger, Customer portal or Superadmin financial write is implemented. Manual toll expenses remain ordinary records; Owner-provided CSV statements use the separate reconciliation workflow below before creating an approved TOLL expense.

Focused real development smoke: after API build and migration, run `pnpm --filter api exec vitest run --config vitest.config.e2e.ts test/commercial.e2e-spec.ts`. This owns disposable exact-ID businesses/operational records/Auth identities and cleans them; named personal accounts are never mutated. The audit history and disabled business tombstones are retained.

## Toll CSV import and reconciliation

`/app/commercial/tolls` is a live Owner worklist linked from Commercial and scoped Rental/Vehicle views. CSV import is an Owner-provided statement, not a live VETC connection or independent proof of payment. It never assigns customer liability, charges a customer or deducts a deposit. The toll source record links to an ordinary Commercial EXPENSE/TOLL movement; it does not form a second money ledger.

The import dialog selects a UTF-8 file (BOM accepted), delimiter (comma/semicolon/tab), explicit column mapping by index, timestamp interpretation and VND grouping before asking the server for a preview. Limits are **64 KiB CSV, 200 nonblank logical data records plus a header, 32 columns and 2,000 characters/cell**; quoted delimiters, doubled quotes and multiline descriptions are supported. A bounded 256 KiB JSON envelope on toll import routes accommodates JSON escaping, with compression rejected; other route parser limits stay unchanged. Only normalized records and hashes are persisted, not raw CSV contents. Syntax/encoding errors reject the file; normalized per-row errors and duplicate/conflict classifications are shown before any write.

Dates are explicitly ISO with offset, ISO local or day/month/year local; local formats use the selected fixed UTC offset (default +07:00). Invalid calendar dates, clock values and offsets are rejected. VND is a positive whole-number string up to **999999999999999**; choose plain integers or dot/comma thousands grouping explicitly. No fractional/negative/zero amounts, scientific notation or silent money/date inference is accepted. Plates reuse Fleet normalization; source names are trimmed/lowercased and references remain case-sensitive. A SHA-256 fingerprint uses normalized plate, UTC timestamp, exact amount and normalized station. Reference-backed rows deduplicate within business/source/reference; reference-free rows use business/source/fingerprint. Conflicting references and ambiguous collisions require review; different references are not silently merged. Changes to descriptions do not invent a different financial transaction.

POST `/tolls/imports/preview` requires `commercial.read` and returns row validation, suggested vehicle/rental, possible prior expense IDs and summary without writing. POST `/tolls/imports` requires `commercial.manage`, a fresh matching preview hash, unique selected row numbers and an idempotency UUID. Confirm reparses/rechecks under the tenant lock, persists one batch plus selected normalized rows/audit atomically and counts already imported duplicates. Reusing a batch key with different content/selection conflicts; retries do not duplicate rows. Tenant/source/reference/fingerprint constraints back up the application lock. No browser table writes are granted; all toll tables enable active-Owner read RLS and preserve historical actor UUIDs.

GET `/tolls` supports bounded pagination plus status/vehicle/rental/from/until filters; dates include an explicit offset and use [from,until). GET `/tolls/:id` returns the latest 100 review snapshots (vehicle/rental/status/version, actor/reason/time), current suggestions and linked movement/correction status; older immutable events remain stored. Suggestions match exact normalized tenant plates and ACTIVE/COMPLETED rentals containing the toll time inside their actual [handedOverAt,returnedAt) interval (ACTIVE uses server time). Missing, cancelled, unstarted or ambiguous rentals are not auto-assigned. Imported rows require explicit Owner review even for a single suggestion. PATCH `/tolls/:id/review` confirms/changes vehicle/rental or ignores a row with a required reason and current version. Overrides are historical, not inferred liability.

POST `/tolls/:id/record` records a reviewed MATCHED row with an explicit reason/version and acknowledgment when a possible duplicate exists. Existing unreversed EXPENSE/TOLL movements with the same tenant vehicle/amount within ±5 minutes are surfaced as possible duplicates, never silently merged. POST `/tolls/record` accepts at most 20 explicitly selected `{id,version}` items and a reason; only currently unambiguous, individually confirmed rows without duplicate warnings qualify. All selected rows succeed or roll back together. Recording uses Commercial's shared insertion/category/scope/date/exact-VND checks and audit inside the same locked transaction as the toll movement link, so retry/concurrent requests cannot double book. A recorded source remains linked even when its movement is corrected through the existing Commercial reversal flow; it is not automatically rebooked.

The shared FormDialog provides mapping/preview/review/record confirmation, per-row errors, state/version feedback and dirty/pending protection. Worklist filters retain scope and display station/time/plate/exact VND, suggestions, review state and navigation to vehicle/rental/movement. Tenant switches reload and abort/discard old draft state. No provider credentials, scraping, live integration simulator, bank settlement, customer/deposit charge, scheduler or billing behavior was introduced.

## Operational alerts

`GET /api/v1/alerts` and `/app/alerts` are live read-only Owner features protected by `alert.read`. They derive current conditions from authoritative tenant data; there is no persisted inbox, acknowledgment state, migration, scheduler or notification delivery. Active profile/business/Owner membership is checked by the existing guards and rechecked in the same SQL statement that returns the page. Platform-only operators, deferred Customer and legacy roles receive no alert permission. Foreign or mismatched vehicle/rental filters return `404 ALERT_SCOPE_NOT_FOUND` without exposing other tenant records.

Vehicle compliance alerts are described in the fleet section above. Only ACTIVE rentals generate rental alerts: end before database `asOf` is overdue/CRITICAL; end from `asOf` through the next 24 hours is due soon/WARNING. GPS alerts require an active vehicle/device, current assignment already begun, and its latest TEST fix recorded within that assignment and no later than `asOf`. Age over 120 seconds is STALE/WARNING, over 600 seconds OFFLINE/CRITICAL, following existing freshness thresholds. No-data, unassigned, ended/future assignments and future fixes do not fabricate alerts. These are timestamp conditions on TEST data, not proof of physical tracker connectivity.

The API accepts page/limit (maximum 100), kind, severity, vehicleId and rentalId. A single database `statement_timestamp()` drives rows and counts. Counts respect entity filters before kind/severity; rows sort by severity, reference time and stable derived ID. Only bounded page metadata is returned; a lateral indexed lookup selects one point per assignment, without returning raw coordinates/UIDs or full history. IDs deduplicate current conditions by rule/entity and are not authorization credentials. Conditions disappear when authoritative data no longer matches; there is no permanent event history.

The Owner inbox shows severity, relevant time, explicit GPS TEST labels, actionable Rental/Vehicle links and scoped counts with useful empty/loading/error states. Filters/page changes preserve content position. It refreshes every 60 seconds while visible and on return to the tab; tenant switching reloads and resets client state. No push/email, cron, VETC, billing, geofence or speculative alert is implemented.

## Reports and CSV export

`/app/reports` is a live read-only Owner view protected by `report.read`. `GET /reports/summary` returns recorded-movement revenue, expenses and estimated profit (reusing Commercial's exact-VND summary), a monthly series in `Asia/Ho_Chi_Minh`, rental counts by current status (rentals starting in the window), and rented-time utilization per active vehicle (top 50 by revenue) plus a fleet aggregate. Windows use explicit offsets, default to the previous 30 days and cannot exceed 366 days; the UI treats the end day as inclusive and sends the next Vietnam midnight. Utilization uses actual handover/return times when present, otherwise the scheduled interval, clipped to the window; it is an estimate, not an accounting figure.

`GET /reports/export/{vehicles|customers|rentals|movements}` returns UTF-8 CSV with BOM, at most 10,000 rows (`422 REPORT_ROW_LIMIT` otherwise). It runs under the tenant lock with the usual active Owner/profile/business recheck and writes a redacted `report.export` audit event (kind only). Identity/licence numbers, addresses and notes are never exported, and cells starting with `= + - @` or control characters get a leading apostrophe. The web route handler `app/app/reports/export/[kind]` proxies the download so the bearer never appears in a URL.

## Production hardening and CI

The API adds `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, a restrictive `Permissions-Policy`, `Cross-Origin-Resource-Policy: same-site` and, in staging/production, HSTS to every response. A process-local fixed-window limiter allows `RATE_LIMIT_PER_MINUTE` (default 300, 10–100000) requests per client IP per minute and returns `429 RATE_LIMITED` with `Retry-After`. Health checks, CORS preflight and the authenticated GPS webhook (own limits) are exempt. `X-Forwarded-For` is ignored unless `TRUST_PROXY=true`; enable it only behind a reverse proxy that appends the client address. Counts are per process, so gateway limits remain required in production. The web app sets framing/referrer/permissions headers (and HSTS in production builds); a nonce-based CSP is deferred because the theme initializer and Leaflet tiles need it.

`GET /api/v1/health` is liveness. `GET /api/v1/health/ready` runs `select 1` with a 3-second timeout and returns `503 NOT_READY` without failure details; Docker `HEALTHCHECK` uses it for the API and `/login` for the web. In staging/production `loadConfig` refuses `ALLOW_DEMO_SEED=true` and a missing `SUPABASE_SECRET_KEY`.

GitHub Actions (`.github/workflows/ci.yml`) runs on push to `main` and pull requests with Node 24.21.0/pnpm 11.19.0: frozen install, typecheck, lint, `pnpm test` (API vitest + web `node --test`), build, a contracts-drift check (`pnpm openapi` then `git diff --exit-code packages/contracts`, using dummy non-secret env) and API/web Docker builds without pushing. CI never uses a real Supabase project or secret.

## Background jobs

`JobScheduler` (`apps/api/src/jobs`) is OFF unless `JOBS_ENABLED=true`; each job also needs its own mode: `JOB_GPS_RETENTION` and `JOB_EVIDENCE_RETENTION` accept `off` (default), `dry-run` (count only) or `apply` (deletes). `JOB_INTERVAL_MINUTES` (5–1440, default 60) and `JOB_MAX_TENANTS_PER_RUN` (default 200) bound each run. A run holds a session advisory lock so only one API replica executes at a time, never overlaps its predecessor and treats invalid configuration as disabled. GPS retention reuses `runRetention` per ACTIVE tenant (30-day rule, latest fix of each current assignment kept; apply deletes at most three batches of 1,000 per tenant). Evidence retention reuses `EvidenceRetentionWorker.runBatch` (50 candidates). Evidence `apply` is **skipped**, never downgraded, unless `retentionDeletionEnabled()` allows irreversible deletion: development keeps its exact-project rule; staging/production require `EVIDENCE_RETENTION_DELETE_ENABLED=true` and `EVIDENCE_RETENTION_DELETE_CONFIRM` equal to the Supabase project ref. Logs contain only job name, mode, outcome and counts. Superadmin → Cài đặt hệ thống shows mode and the per-process last run. Recommended rollout: `dry-run` for a week, review counts, then `apply` for one job at a time. The unchanged evidence janitor for expired uploads continues to run independently.

## Launch checklist

Nothing below is performed by an implementation stage; each item needs a human owner. Do staging first, repeat for production, and never run seeds, E2E or maintenance commands against either.

1. **Projects and data.** Create a separate Supabase project per environment. Apply `supabase/migrations` with `pnpm db:migrate` (the script refuses a mismatched project ref). Enable backups/point-in-time recovery on the paid plan and rehearse one restore before launch. Create the `inspection-images` and `inspection-videos` buckets (`evidence:storage` is restricted to the development project, so create them in the Dashboard as private buckets or extend the command deliberately).
2. **Auth (Dashboard, per environment).** Disable public/email signup; set the Site URL and allowlist `${WEB_ORIGIN}/auth/confirm`; configure SMTP and the recovery template from `supabase/templates/recovery.html`; set password strength and leaked-password protection (paid plan); keep recovery OTP expiry short; review the email rate limit used by `/forgot-password`.
3. **First Superadmin.** Seeding is retired. Create the identity and `user_profiles` + `platform_memberships(PLATFORM_OPERATOR)` rows through a reviewed trusted administrator process (SQL editor or a one-off script run by an administrator), then provision businesses and Owners from `/superadmin`. Customers are provisioned by Owners from Customer detail.
4. **Configuration.** API env: `APP_ENV=production`, HTTPS `WEB_ORIGIN`, `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY`, session-pooler `DATABASE_URL` with TLS CA, `GPS_TRACCAR_TOKEN` only if a GPS feed is exposed, `RATE_LIMIT_PER_MINUTE`, `TRUST_PROXY=true` only behind your proxy, `ALLOW_DEMO_SEED` unset/false. Web env: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `NEXT_PUBLIC_API_BASE_URL` (build args) and `API_INTERNAL_URL`. Keep secrets in the platform secret store, not in images or Git.
5. **Network.** Terminate TLS at a reverse proxy in front of loopback-bound containers; add per-IP rate limits, request/body timeouts (Node's default request deadline is five minutes) and connection limits for the GPS webhook; forward the client address in `X-Forwarded-For` and set `TRUST_PROXY=true`. Add a CSP (nonce-based; the theme initializer and OpenStreetMap tiles need allowances) at the proxy or in Next.js. Use a paid tile service if traffic exceeds OpenStreetMap's policy.
6. **Deploy and verify.** Build with the `Dockerfile` targets (`api`, `web`); containers have `HEALTHCHECK`s. After each deploy run `pnpm smoke --api=<api-url> --web=<web-url> --production` (unauthenticated, read-only) and then the manual checks in `STAGE_OUTPUT.md` with a disposable tenant. CI (`.github/workflows/ci.yml`) must be green before deploying.
7. **Background jobs.** Leave `JOBS_ENABLED` off at first. Turn on `dry-run` for GPS and evidence retention, review counts and the Superadmin settings page, then enable `apply` one job at a time (evidence deletion also needs `EVIDENCE_RETENTION_DELETE_ENABLED=true` and `EVIDENCE_RETENTION_DELETE_CONFIRM=<project ref>`).
8. **Operations.** Ship the JSON request logs (`requestId`, path, status, duration; no bodies or credentials) to central storage and alert on 5xx rate, `/health/ready` failures, migration drift and job `failed` outcomes. Rotate `SUPABASE_SECRET_KEY`, `GPS_TRACCAR_TOKEN` and database passwords on a schedule and after any exposure. Roll back by redeploying the previous image; migrations are forward-only, so write a compensating migration rather than editing history.
9. **Business and legal sign-off.** Have a qualified lawyer review the default Vietnamese contract terms; confirm retention periods; connect a notification/payment provider through `integrations` and a physical GPS tracker feed only after their own security and data-protection review. GPS remains a Traccar TEST feed until then.
