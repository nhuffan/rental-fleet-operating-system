# AI rules

- Read README.md, docs/development.md and relevant app instructions before editing. Keep changes within the user's request and preserve unrelated work.
- README gives a short project introduction and quick launch commands for Web/API. Keep detailed current development/architecture instructions in docs/development.md; neither file is a stage log.
- Root STAGE_OUTPUT.md is the sole permanent accumulated stage log; never delete it or replace it with individual stage files. Keep chronological "## Stage N output" sections with only "### Delivery" and "### Cases to test", following the user’s concise format. Delivery uses 1–3 short bullets describing user-visible results and essential TEST/PREVIEW/deferred boundaries. Cases to test normally uses 3–5 short manual checkboxes (fewer for foundation/unverified stages) with a concrete action and expected result; retain unverified status without claiming a test ran. Merge follow-ups into their stage and keep one section per stage. Do not add command transcripts, test counts, PIDs, commit narratives, technical recaps or extra verification/handoff sections; current operating details belong in docs/development.md and history remains in Git. Before a stage commit, update this file with its actual delivery and useful test cases. Exactly ONE implementation commit per stage contains source, migrations, contracts, tests, rule/doc changes and output; Git is authoritative for the resulting SHA. Never create an extra commit or amend solely to record its SHA.
- After an authorized implementation commit, push the current branch to its configured remote unless the user explicitly requests otherwise. Never force-push or overwrite unrelated remote work.
- Input stage plans are task inputs, not permanent reports. Do not archive them as additional repository Markdown or recreate a per-stage documentation directory. Recover accurate historical results from Git and retain concise summaries in root STAGE_OUTPUT.md; explicitly mark unknown historical details as not verified.
- Do not generate separate stage logs, validation/architecture/recap reports, JSON QA manifests or screenshots by default. Create visual evidence only when the current stage or user explicitly requests it. Necessary source, tests, migrations and generated build contracts remain allowed. Keep current operating rules in docs/development.md and the introduction/quick launch commands in README.md; preserve useful policy before retiring obsolete documents or artifacts.
- Use pnpm and preserve its lockfile and pinned Node runtime. Prioritize feature implementation; verify changed paths, core authorization/security invariants, build/typecheck and lint for touched workspaces. Generate OpenAPI/contracts after API changes. Defer broad historical E2E, exhaustive browser/viewport matrices, visual comparisons, load benchmarks and evidence collection to a dedicated Final Validation stage unless a concrete regression/security issue requires them. Never defer a failing critical security check.
- Ask before starting a server unless the user explicitly authorizes it in the current task. Record owned sessions/PIDs/ports. Stop all servers/watchers you started before finishing, including on failure, and verify they exited. Never stop user-owned processes or use broad kill commands. Leave servers running only when explicitly requested.
- Keep real env files and .env.demo.json out of Git and logs. Never send database credentials or server keys to the browser. TLS certificate/hostname verification is mandatory for database access.
- Supabase supplies identity; NestJS owns authorization. Never authorize using user_metadata. Check active profile, business and membership, then permission. Every tenant resource query must include the verified business ID. Global platform reads require the independent platform principal/permission guards; tenant roles or a selected business never grant platform access. Keep platform audit separate from tenant audit.
- Keep admin writes and audit events in one transaction; recheck authorization under the tenant lock. OWNER is the sole tenant role; member creation grants OWNER and updates change status only. Preserve an active owner. Superadmin uses independent PLATFORM_OPERATOR membership; Customer is a portal-only identity (Auth user + active profile linked to one tenant customer through `customer_portal_accounts`, never a business/platform membership) with read-only access to its own non-draft rentals and issued contracts through the independent `/portal` API, and receives no administration grant.
- Keep all schema changes in supabase/migrations using the Supabase CLI. Drizzle is the query layer; do not introduce a competing migration history. Enable RLS on exposed tables; direct Data API writes are denied.
- Development project: eeryymswcufnebibigqf. Never seed/demo-test against staging or production. Do not change other Supabase projects based on account defaults. Named personal accounts in ignored .env.accounts.json must never be disabled, demoted, reset or deleted by tests. Persistent demo seeding is retired; real E2E must own disposable exact-ID fixtures and clean their Auth identities.
